# Hito F1-H0: Cimientos

**Versión:** 1.1
**Fecha:** 19 de octubre de 2026
**Origen:** sección 8 del Documento de Arranque v1.0, con las correcciones de la auditoría (IC-06, IC-11, DA-03, DA-08, OM-10, OM-12).

## 1. Objetivo

Dejar listo un entorno reproducible, una estructura de proyecto que haga cumplir la arquitectura y un comando único que decida si algo está terminado. **No se construye ninguna funcionalidad de negocio.**

## 2. Fuera de alcance

Tablas de negocio, usuarios, autenticación, endpoints distintos a la ruta de salud, comandos de consola de negocio, seeders de negocio y todo lo que esté en `frontend/`. Tampoco: cachés, colas, subida de archivos ni dependencias que no estén en las tareas.

## 3. Prerrequisitos (los hace el responsable)

- Docker y Docker Compose instalados.
- Carpeta del proyecto creada, con `AGENTS.md` en la raíz y estos archivos en `docs/`: `requisitos.md`, `arquitectura.md`, `alcance-fases.md`, `plan-fase-1.md`, `estrategia-pruebas.md`, `convenciones-api.md`, `criterios-aceptacion-fase-1.md`, `decisiones/registro-decisiones.md` y `hitos/f1-h0.md`.
- Repositorio de GitHub creado antes de T10.
- Herramienta del agente configurada.

## 4. Tareas

Cada tarea indica las rutas que se pueden tocar. Todo lo demás requiere aprobación. Cada tarea tiene una lista **No hacer** que forma parte de sus criterios.

### F1-H0-T01. Estructura del repositorio y documentos
- **Rutas:** raíz y `docs/`.
- **Hacer:** crear la estructura de `docs/plan-fase-1.md` (monorepo con `backend/`, `frontend/` vacío con `.gitkeep`, `docs/`, `scripts/humo/`), `.gitignore`, `README.md` con instrucciones de arranque, `CLAUDE.md` con la línea `@AGENTS.md`, y `docs/trazabilidad.md` con su encabezado y sin filas.
- **Aceptación:** la estructura existe; `CLAUDE.md` importa a `AGENTS.md`; el primer commit queda en la rama principal.
- **No hacer:** código de aplicación, contenido dentro de `frontend/`, modificar los documentos de `docs/`.

### F1-H0-T02. Docker Compose, Makefile y roles de base de datos
- **Rutas:** `docker-compose.yml`, `Makefile`, `backend/docker/`.
- **Hacer:** servicios `app` (PHP 8.4 con Composer, extensiones para PostgreSQL y cobertura) y `db` (PostgreSQL 16) con volumen y comprobación de salud; base de datos de desarrollo y una de pruebas; dos roles de base de datos: un propietario que ejecuta las migraciones y un rol de aplicación sin permiso de `UPDATE` ni `DELETE` sobre tablas `*_historial` (se aplica en T08); archivo `.env.example`; objetivos `levantar`, `bajar` y `consola`.
- **Aceptación:** `make levantar` deja ambos servicios en estado saludable; la aplicación alcanza la base con el rol de aplicación; `make bajar` los detiene sin errores; los dos roles existen en la base de desarrollo y en la de pruebas.
- **No hacer:** servicios extra (Redis, correo, colas), Laravel Sail, secretos reales en `.env.example`.

### F1-H0-T03. Proyecto Laravel 13 y ruta de salud
- **Rutas:** `backend/`.
- **Hacer:** instalar Laravel 13; configurar PostgreSQL, zona horaria UTC e idioma `es` (zona de presentación America/Mexico_City como configuración); crear `GET /api/v1/salud` que devuelva el estado de la aplicación y de la base de datos.
- **Aceptación:** la ruta responde 200 con ambos estados en `ok`. Hay una prueba de API para ese caso. (La respuesta 503 con el formato de error se prueba en T09, cuando ese formato existe.)
- **No hacer:** autenticación, otras rutas, paquetes de Laravel no listados (Sanctum se instala en H1).

### F1-H0-T04. Herramientas de calidad y comando de verificación
- **Rutas:** `backend/` (configuración y `composer.json`), `Makefile`, `scripts/humo/`.
- **Hacer:** instalar Pest, Pest Arch, Laravel Pint, Larastan (nivel 6) y la cobertura; definir el script `composer verificar` (estilo, análisis, pruebas con cobertura, `composer audit`) y los objetivos `make verificar`, `make pruebas`, `make migrar`, `make fresh` y `make humo` (ejecuta todos los `scripts/humo/humo-h*.sh` presentes); cobertura **medida y reportada, sin umbral que bloquee** hasta H1.
- **Aceptación:** `make verificar` pasa en un árbol limpio y **falla** al introducir a propósito un error de estilo, un error de tipos y una prueba rota (el agente lo demuestra y lo revierte); el reporte de cobertura se genera.
- **No hacer:** Infection (llega en H2), umbrales de cobertura que bloqueen, reglas de análisis desactivadas.

### F1-H0-T05. Estructura DDD y pruebas de arquitectura
- **Rutas:** `backend/src/`, `backend/tests/Arch/`, `backend/composer.json`, `backend/bootstrap/providers.php`.
- **Hacer:** crear los contextos de `docs/arquitectura.md` (sección 4): Compartido, Identidad, Plantel, Academico, Competencia, Rendimiento, CondicionFisica, Salud, Alertas (con `Dominio`, `Aplicacion` e `Infraestructura` vacías) y Consultas (solo `Aplicacion` e `Infraestructura`); autocarga `Src\`; un proveedor de servicios por contexto; pruebas que verifican: Dominio sin dependencias del framework, Aplicación sin dependencia de Infraestructura, y ningún contexto importa el dominio de otro salvo Compartido (incluidos `Compartido/Dominio/Eventos` y la interfaz `AlcanceDeJugadores`, que otros contextos pueden usar).
- **Aceptación:** las pruebas de arquitectura pasan y **fallan** al agregar una violación de ejemplo (que luego se elimina).
- **No hacer:** clases de negocio, eventos reales, la interfaz `AlcanceDeJugadores` (se crea en H1), migraciones.

### F1-H0-T06. Núcleo compartido
- **Rutas:** `backend/src/Compartido/`, pruebas correspondientes.
- **Hacer:** objeto de valor `Identificador` (UUID v7), interfaz `Reloj` para controlar el tiempo en pruebas, interfaz del usuario actual y una excepción base `ReglaDeNegocioViolada` con código estable.
- **Aceptación:** pruebas unitarias sin base de datos: un identificador generado es UUID v7 válido y se rechaza uno inválido; el reloj se puede fijar; la excepción expone su código.
- **No hacer:** otros objetos de valor, implementación del usuario actual (llega con la autenticación en H1).

### F1-H0-T07. Macros de migración y extensión `citext`
- **Rutas:** `backend/src/Compartido/Infraestructura/`, `backend/database/migrations/`, `backend/app/Providers/`.
- **Hacer:** macros `auditoriaBasica()` e `historial()` para el constructor de esquema (secciones 6 y 9 de `docs/arquitectura.md`); migración del grupo 000 que habilita `citext` en `backend/database/migrations/compartido/`; registro de las subcarpetas de migraciones por contexto en el proveedor de servicios con `loadMigrationsFrom`; formato de nombre `AAAA_MM_DD_GGGSSS_descripcion` (sección 8.1 de `docs/arquitectura.md`).
- **Aceptación:** una prueba de integración crea una tabla temporal con cada macro y confirma, consultando el catálogo de PostgreSQL, los nombres y tipos de las columnas, las claves foráneas y los índices; `make fresh` y la reversión funcionan.
- **No hacer:** tablas de negocio ni sus migraciones.

### F1-H0-T08. Registro de historial de solo inserción
- **Rutas:** `backend/src/Compartido/` y pruebas.
- **Hacer:** un componente que escribe el cambio y su registro de historial en la misma transacción (consecutivo por entidad, valores anteriores y nuevos, usuario y fecha), y un disparador reutilizable que rechaza `UPDATE` y `DELETE` en una tabla de historial; la revocación de `UPDATE` y `DELETE` al rol de aplicación de T02 sobre una tabla de historial de prueba.
- **Aceptación:** con una tabla de prueba, (a) un cambio genera su registro con versión consecutiva; (b) si la transacción falla, no queda ni el dato ni el historial; (c) un `UPDATE` o `DELETE` sobre el historial es rechazado por la base de datos, tanto por el disparador como por la falta de permiso del rol de aplicación.
- **No hacer:** historial de entidades de negocio, consulta de historial (HU-26, llega en H7).

### F1-H0-T09. Convenciones de la API
- **Rutas:** `backend/app/Exceptions/`, `backend/bootstrap/`, `backend/lang/es/`, `backend/app/Http/`, `backend/tests/`, `docs/api/openapi.yaml`.
- **Hacer:** manejador de excepciones que devuelva el formato de error de `docs/convenciones-api.md` (404, 401, 403, 409, 422, 500, 503 y errores de regla de negocio); mensajes en `lang/es`; que todas las rutas de `/api` respondan JSON; un recurso base de paginación y una estructura de respuesta con `datos` y `advertencias` opcional; `openapi.yaml` inicial con la ruta de salud y el esquema de error; prueba de que cada ruta de `/api/v1` está documentada y cada ruta documentada existe; prueba de que ningún texto visible está escrito fuera de `lang/es`. **Proponer la librería de validación contra OpenAPI y esperar aprobación antes de instalarla.**
- **Aceptación:** cada tipo de error devuelve el formato esperado con mensaje en español; si la base no responde, `GET /api/v1/salud` devuelve 503 con el formato de error (prueba de API); en producción no se filtran trazas; una prueba valida la respuesta de salud contra el contrato.
- **No hacer:** instalar la librería de contrato sin aprobación, endpoints de negocio.

### F1-H0-T10. Integración continua
- **Rutas:** `.github/workflows/`.
- **Hacer:** flujo de GitHub Actions al hacer push y solicitud de cambio: PostgreSQL como servicio, PHP 8.4, instalar dependencias, `migrate:fresh` y `composer verificar`.
- **Aceptación:** el flujo pasa en la rama del hito; falla si se rompe una prueba (se demuestra con una rama temporal que se descarta).
- **Previo:** el repositorio debe existir en GitHub y la rama principal debe estar protegida por el responsable.
- **No hacer:** despliegue, publicación de paquetes, secretos en el flujo.

### F1-H0-T11. Guion de humo y cierre de H0
- **Rutas:** `docs/`, `scripts/humo/`, `AGENTS.md`.
- **Hacer:** escribir `scripts/humo/humo-h0.sh` (comprueba `GET /api/v1/salud`); completar `docs/trazabilidad.md` con la estructura para HU-01 a HU-30, RN-01 a RN-23 y RNF-01 a RNF-11, con una columna de pruebas vacía y otra de hito; registrar en `docs/decisiones/` cualquier decisión tomada durante H0 (por ejemplo, la librería de contrato y el nivel de Larastan); ajustar `AGENTS.md` solo si algún comando real difiere de lo documentado.
- **Aceptación:** la compuerta de `docs/plan-fase-1.md` (sección 4) se cumple; `make humo` termina sin fallas; se crea la etiqueta `f1-h0`.
- **No hacer:** llenar filas de pruebas que todavía no existen.

## 5. Criterios de aceptación de H0

- `make levantar`, `make verificar` y `make humo` funcionan en una máquina limpia siguiendo solo el `README.md`.
- La integración continua está en verde.
- Las pruebas de arquitectura impiden las tres violaciones principales.
- Existe una ruta de salud documentada en el contrato y probada, incluido el 503.
- Las pruebas de rutas documentadas y de textos fuera de `lang/es` están activas.
- Los roles de base de datos existen y el historial rechaza `UPDATE` y `DELETE`.
- Ninguna tabla de negocio fue creada.
- El reporte final incluye la sección "Fuera de alcance" y no hay trabajo no pedido.
