# Reporte F1-PT07: candado de `make verificar` y procesos huérfanos

**Fecha:** 31 de octubre de 2026 · **Rama:** `tecnico/pt-07` (desde `main`, `318d715`)
**Commits:** `16fcc07` (primera versión, con el pulso por tubería; falló en PowerShell, §7) y la corrección que contiene este reporte (`F1-PT07: recetas de un solo comando y vigilante por EOF`).
**Origen:** PT-07 de `docs/decisiones/registro-decisiones.md` §3. El responsable aprobó dos planes el 31/10/2026: el primero cubre `verificar`, `pruebas` y `mutacion` y fija un tope de `timeout 20m`; el segundo, tras el fallo en PowerShell, pide recetas de un solo comando y un vigilante que dependa solo de EOF.
**Estado:** **Resuelto** el 1/11/2026, con la corrección `d0a2059`. Las pruebas 1 a 6 del agente pasan (§3 y §4) y la corrida de Luis en PowerShell confirma el cambio en Windows (§8). Quedan dos limitaciones abiertas (§6).

## 1. Problema

- Dos corridas a la vez comparten la base de pruebas `gestordep_pruebas` y se rompen el esquema entre sí (570 fallos y 27 min 21 s en H2; `f1-h2-fix-e-m3.md`).
- Docker no termina el proceso interno cuando muere el cliente de `docker compose exec`: un `composer verificar` huérfano sigue corriendo dentro del contenedor.

## 2. Cambio

**`backend/bin/con-candado.sh`** (bash; se ejecuta dentro del contenedor `app`):

1. **Candado:** abre `/tmp/gestordep-pruebas.lock` (en el contenedor, no en el montaje de Windows) y toma `flock -n`. Si otra corrida lo tiene, termina en el acto con el código **75** y el mensaje «Otra corrida de verificar, pruebas o mutacion usa la base de pruebas en este contenedor; espera a que termine.». Todos los procesos del comando heredan el descriptor: el candado sigue tomado mientras viva cualquiera de ellos.
2. **Tope:** el comando corre como `setsid timeout --kill-after=10s 20m <comando>`, en un grupo de procesos propio. A los 20 minutos termina con el código **124** y el mensaje «La corrida supero el tope de 20 minutos y se termino.».
3. **Vigilante, solo por EOF:** lee la entrada estándar que reenvía `docker compose exec` (por el descriptor 3, con `read` sin `-t`) hasta el fin de la entrada.
   - **Si el EOF llega en los primeros 2 s,** la entrada estaba cerrada desde el principio (entrada nula). El vigilante se desactiva y avisa con «Entrada estandar cerrada: el vigilante queda desactivado; protegen el candado y el tope de 20 min.». La corrida sigue.
   - **Si llega después,** el cliente murió. El vigilante avisa con «Se perdio el cliente de docker compose exec; se termina la corrida.», envía `TERM` al grupo y, 10 s después, `KILL`.
   - **Una consola sin datos no envía EOF,** así que no mata la corrida.
4. **Al terminar bien o mal,** mata lo que quede del grupo y devuelve el código del comando.

**`Makefile`:** las líneas exactas de las tres recetas son:

```make
verificar:
	docker compose exec -T app bash bin/con-candado.sh composer verificar

mutacion:
	docker compose exec -T app bash bin/con-candado.sh composer mutacion

pruebas:
	docker compose exec -T app bash bin/con-candado.sh php vendor/bin/pest
```

Cada receta es un solo comando, sin tuberías, bucles ni `;`. `make` la ejecuta igual con `cmd.exe` (PowerShell o cmd, sin `sh.exe` en el `PATH`) y con `sh` (Git Bash). El código de salida es el del comando.

**CI:** no cambia. `.github/workflows/verificar.yml` no usa `make`, y cada job tiene su propia base.

### 2.1 Regla del agente para sus corridas

La terminal del agente le da a `make` una entrada nula, y con ella el vigilante se desactiva (§7, a′). Para que el vigilante quede activo, el agente ejecuta en Git Bash:

```bash
make verificar < <(sleep 3600)
```

Lo mismo vale para `make pruebas` y `make mutacion`. Si la corrida muestra el aviso «Entrada estandar cerrada», el vigilante no estuvo activo.

## 6. Limitaciones que siguen

- **Hueco b′:** si muere `docker.exe` y `docker-compose.exe` sigue vivo, el plugin mantiene la conexión y no llega el EOF (§7, b′). La corrida sigue hasta que termine o hasta el tope de 20 min. El candado impide que otra corrida la contamine.
- **`make fresh` y `make humo` sin candado**, por indicación del responsable. Usan la base de desarrollo, pero tampoco tienen vigilante: si muere el cliente, el proceso interno sigue corriendo. Queda anotado para una decisión posterior.
- **Entrada nula o cliente que muere en sus primeros 2 s:** el vigilante no actúa; protegen el candado y el tope de 20 min.

Ctrl+C ya no figura como pendiente: lo probó Luis (§8).

## 7. Fallo en PowerShell (31/10/2026)

**Primera versión (`16fcc07`):** cada receta era `while echo; do sleep 5; done | docker compose exec -T app bash bin/con-candado.sh <comando>`, y el vigilante usaba `read -t 30` (mataba la corrida a los 30 s sin pulso). En Git Bash pasó sus pruebas (dos corridas a la vez, huérfano tras `taskkill /F` en 6 s, cliente sin pulso, tope) y un `make verificar` con código 0 en 673 s (Pest 521 s).

**Resultado de Luis:** `make verificar` en PowerShell falló con el **error 255**. `make levantar` sí funciona.

**Causa:** en Windows, GNU Make solo usa `sh.exe` si lo encuentra en el `PATH`. En el equipo del agente, la terminal de Git Bash lo tiene (`SHELL = C:/Program Files/Git/usr/bin/sh.exe`); en la consola de PowerShell de Luis no, así que `make` ejecuta la receta con `cmd.exe`. `cmd.exe` no entiende `while ...; do ...; done`. `make levantar` funciona porque sus líneas son comandos simples. **La prueba con Git Bash no bastaba:** la receta dependía del shell que encontrara `make`.

**Condiciones del responsable para corregirlo:**
1. Cada receta (`verificar`, `pruebas`, `mutacion`) es un solo comando, sin tuberías, bucles ni `;`, y funciona en cmd.exe, PowerShell y Git Bash.
2. El vigilante no mata la corrida por falta de señal cuando la entrada es una consola sin datos. La primera versión lo hacía, con `read -t 30`.

**Evidencia en PowerShell** (Docker Compose v5.3.1), con guiones de sondeo temporales en `backend/build/`, que ya se borraron. No se tocó `make verificar`.

| # | Comprobación | Resultado |
|---|---|---|
| a | ¿`docker compose exec -T` reenvía la entrada del cliente? | **Sí.** `"linea-desde-powershell" \| docker compose exec -T app bash build/leer-linea.sh` imprime `contenedor leyo: [linea-desde-powershell]` (con el BOM que añade PowerShell). La ayuda de v5.3.1 ya no muestra `-i`, pero la opción existe (`-T -i` responde 0) y la entrada se reenvía sin pasarla |
| a′ | Entrada **nula** (la herramienta del agente, un ejecutor de tareas del editor, `make < NUL`) | El contenedor recibe **EOF a los 0 s** |
| b | Consola sin datos (ventana nueva con `Start-Process`, nadie escribe) | **Sin EOF** a los 40 s. Tras `taskkill /F /T` sobre `docker.exe` (y sus hijos `docker-compose.exe` y `conhost.exe`), **EOF en menos de 3 s** |
| b′ | `taskkill /F` solo sobre `docker.exe`, sin `/T` | `docker-compose.exe` sigue vivo y mantiene la conexión: **sin EOF** a los 10 s. Al matar `docker-compose.exe`, EOF en menos de 3 s |

**Conclusión:** a y b se cumplen, así que un vigilante que dependa solo de EOF cumple la condición 2. Pero con la entrada nula el EOF llega a los 0 s, y ese vigilante mataría la corrida en el acto. Ahí entran las corridas del agente, que es donde apareció el huérfano de H2. De ahí el margen de 2 s y la regla del agente (§2 y §2.1), aprobados por el responsable.

## 8. Evidencia de Windows y Ctrl+C (1/11/2026)

**Lo que confirmó Luis en su equipo, en PowerShell, sobre `d0a2059`.** El agente no tiene la salida completa, solo este resumen del responsable:

- `make verificar` completo con **código 0**.
- El candado rechaza una segunda corrida.
- **Ctrl+C dos veces:** después de cada intento, el contenedor quedó limpio.
- **`docker top`** no muestra procesos de la corrida.

Con esto se cumple la condición de cierre (§5) y PT-07 pasa a «Resuelto».

**El segundo Ctrl+C no mostró «Se perdio el cliente de docker compose exec; se termina la corrida.»** (el primero sí). Por `docker top`, no quedaron procesos de la corrida: la limpieza funcionó aunque el mensaje no apareciera.

**Hipótesis, sin comprobar.** No hay registro del lado del contenedor de ese intento, así que no se puede saber cuál ocurrió:

1. **El vigilante terminó junto con la corrida antes de imprimir.** En `con-candado.sh`, el vigilante escribe el mensaje *antes* de enviar `TERM` al grupo, y vive fuera del grupo del comando. Matar el grupo no lo calla. Esta hipótesis solo encaja si el comando terminó antes por otra vía, por ejemplo si la interrupción llegó al proceso del contenedor. En ese caso `wait` regresa, el guion mata al vigilante y este no llega a imprimir. El agente no comprobó si `docker compose exec` reenvía Ctrl+C al proceso del contenedor.
2. **La salida se perdió con la señal.** El mensaje va por la salida de errores del `exec` y vuelve al cliente de `docker compose`. Si el cliente ya había terminado o dejado de leer cuando el vigilante escribió, el texto se pierde aunque se haya escrito. En el primer intento el cliente pudo seguir leyendo un instante más.

Para distinguirlas haría falta escribir en el contenedor un registro con hora de cada paso del vigilante. Eso no se hizo, porque no es necesario para cerrar PT-07.
