# Reporte F1-PT07: candado de `make verificar` y procesos huérfanos

**Fecha:** 31 de octubre de 2026 · **Rama:** `tecnico/pt-07` (desde `main`, `318d715`) · **Commit:** el que contiene este reporte (`F1-PT07: candado de make verificar y huerfanos`)
**Origen:** PT-07 de `docs/decisiones/registro-decisiones.md` §3; plan aprobado por el responsable el 31/10/2026, con condiciones (cubre `verificar`, `pruebas` y `mutacion`; tope de `timeout 20m`; evidencia en Windows antes de cerrar).
**Estado:** implementado y probado en el equipo del agente. **PT-07 sigue «En implementación»** hasta que Luis entregue la evidencia de Windows (§5).

## 1. Problema

- Dos corridas a la vez comparten la base de pruebas `gestordep_pruebas` y se rompen el esquema entre sí (570 fallos y 27 min 21 s en H2; `f1-h2-fix-e-m3.md`).
- Docker no termina el proceso interno cuando muere el cliente de `docker compose exec`: un `composer verificar` huérfano sigue corriendo dentro del contenedor.

## 2. Cambio

**Nuevo, `backend/bin/con-candado.sh`** (bash, se ejecuta dentro del contenedor `app`):

1. **Candado:** abre `/tmp/gestordep-pruebas.lock` (en el contenedor, no en el montaje de Windows) y toma `flock -n`. Si otra corrida lo tiene, termina en el acto con el código **75** y el mensaje «Otra corrida de verificar, pruebas o mutacion usa la base de pruebas en este contenedor; espera a que termine.». Todos los procesos del comando heredan el descriptor: el candado sigue tomado mientras viva cualquiera de ellos.
2. **Tope:** el comando corre como `setsid timeout --kill-after=10s 20m <comando>`, en un grupo de procesos propio. A los 20 minutos termina con el código **124** y el mensaje «La corrida supero el tope de 20 minutos y se termino.».
3. **Vigilante:** lee el pulso del Makefile por la entrada estándar (`read -t 30`). Si llega el fin de la entrada (el cliente murió) o pasan 30 s sin pulso, envía `TERM` al grupo y, 10 s después, `KILL`.
4. **Al terminar bien o mal**, mata lo que quede del grupo y devuelve el código del comando.

**`Makefile`:** las líneas exactas de las tres recetas son:

```make
verificar:
	while echo; do sleep 5; done | docker compose exec -T app bash bin/con-candado.sh composer verificar

mutacion:
	while echo; do sleep 5; done | docker compose exec -T app bash bin/con-candado.sh composer mutacion

pruebas:
	while echo; do sleep 5; done | docker compose exec -T app bash bin/con-candado.sh php vendor/bin/pest
```

El bucle envía una línea cada 5 s y se detiene cuando falla el `echo`, a más tardar 5 s después de que termine `docker`. El código de salida de la receta es el de `docker`, que es el del comando. El bucle es necesario porque la entrada de `make` puede estar cerrada desde el principio (así ocurre en la terminal del agente): sin él, el vigilante vería el fin de la entrada en el acto.

**CI:** no cambia. `.github/workflows/verificar.yml` no usa `make`, y cada job tiene su propia base.

## 3. Pruebas manuales

Son pruebas de shell y del Makefile, no de Pest. Para no correr nada en paralelo con `make verificar`, las pruebas 1 a 5 usan `sleep`, `false` o `exit 3` como comando. Los procesos del contenedor se leen de `/proc/*/cmdline` y `/proc/*/stat`, porque la imagen no trae `ps` ni `pkill`.

| # | Prueba | Resultado |
|---|---|---|
| 1 | Corrida A (`sleep 40`) y, 4 s después, corrida B (`sleep 5`) | B termina con el código **75** y el mensaje del candado. A termina con el código 0 |
| 2 | El grupo termina cuando la corrida acaba bien | Durante A: `con-candado.sh` (pgid 31), `timeout` y `sleep 40` (pgid 38). Al terminar A, el contenedor solo tiene los procesos permanentes y la consulta: **ningún proceso de los grupos 31 ni 38** |
| 3 | Código de salida a través de la tubería (con el `sh.exe` de Git que usa `make`) | `false` devuelve **1**; `sh -c "exit 3"` devuelve **3** |
| 4 | **Huérfano:** corrida `sleep 300`; se matan a la fuerza (`taskkill /F`) `docker.exe` y `docker-compose.exe` del cliente | A los **6 s**, ningún proceso `sleep 300` en `/proc` y el candado libre (`flock -n` sobre el archivo, código 0) |
| 5 | Cliente vivo y sin pulso (`sleep 120 \| docker compose exec ... sleep 100`) | El vigilante escribe «Se perdio el cliente de docker compose exec; se termina la corrida.» y la corrida termina con el código **143** (`TERM`), antes de los 100 s del `sleep`. El cliente tardó 120 s solo porque la tubería esperaba al `sleep 120` de la prueba |
| 6 | Tope de `timeout`, con una copia temporal del guion que usa 3 s en lugar de 20 min (en `backend/build/`, ignorado por git y borrado después) | Código **124** a los 5 s, con el mensaje del tope. Ningún proceso de la corrida quedó vivo |
